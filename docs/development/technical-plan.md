# 技术与开发路线

## 当前 Demo

活动室使用手写 HTML、CSS、JavaScript。插画作为房间背景，透明主角、互动入口、可收集物和完成后的招牌构成独立互动层。寻路在预设可走区域内执行，NPC 使用分支与关键词，任务状态保存到浏览器 localStorage。

| 文件 | 职责 |
| --- | --- |
| `demos/rongshuli-room/dist/index.html` | 场景、人物入口、对话和制作面板 |
| `demos/rongshuli-room/dist/style.css` | 场景、人物与界面的展示和响应式布局 |
| `demos/rongshuli-room/dist/game.js` | 行走、交互、对话、背包、设计和回忆 |
| `demos/rongshuli-room/dist/game-state.js` | 任务转换、条件检查、存档恢复和词汇 |
| `demos/rongshuli-room/dist/assets/` | 活动室背景与透明主角 |
| `demos/rongshuli-room/tests/` | 状态测试及完整浏览器流程检查 |

当前 `dist` 是手写源目录，不是构建生成物。静态部署该目录即可，无需前端打包和后端服务。

## 后续架构建议

随着场景和内容增多，逐步分离世界状态、事件定义、能力目标、人物资料、对话与媒体资源。地点和事件使用稳定编号，存档保留版本并处理迁移。内容编辑应支持预览与审核。

场景移动、切换和动画需求增多时，可评估 Phaser 类2D网页框架；若团队更熟悉游戏编辑器，也可验证 Godot 网页导出。技术迁移以原型需求为依据，现有 Demo 未使用这些引擎。

正式账号与跨设备进度需要后端状态服务。实时 NPC 需要角色服务、记忆读取、输出及候选行动检查，并由规则服务确认世界变化。模型密钥仅在服务端保存。

## 验证边界

图形交互、任务与本地存档已做原型。儿童语音识别、实时语音对话、开放回答、长期记忆、完整课程覆盖与运行预算仍需独立验证。语音转写成功不能直接作为发音掌握证据。

先测单个角色对话，再评估小组互动。记录每次游玩的调用、语音、存储与分发成本，结合实际活跃和频次估算，不能仅按 NPC 人数推算。

## 发布与仓库关系

线上活动室是既有 Sites 私有发布版本。本仓库保存可独立运行的开发副本，不导入原 Sites 项目身份、写入凭据和托管仓库历史。GitHub 更新不会自动修改原线上站点；后续发布流程另行配置。
